# Aeliqo 0.3 implementation

Status: implementation and configured live BYOK acceptance complete; exact-source release evidence is recorded by the canonical quality matrix before publication or deployment

## Goal and acceptance

Deliver Aeliqo 0.3 as an adaptive web UI framework driven by validated resource intents. The same runtime must work through application code or an agent transport. Developers own domain meaning, data, authorization, and business effects; Aeliqo owns bounded compilation, evaluation, presentation, adaptation, and lifecycle.

The release keeps the six public packages. It adds high-level subpath APIs, four non-dashboard playground scenarios, complete English documentation, and separate landing/docs/playground routes. Studio is out of scope except for build compatibility. Package publication and production deployment happen only after exact-source release acceptance.

## Current state and constraints

- Started from clean `main` revision `9d20eca` on branch `codex/aeliqo-0.2`; the implementation release line was subsequently raised together to `0.3.0` after npm registry preflight found unreusable `0.2.0` identities.
- Published `0.1.0` packages remain available; 0.3 may intentionally break source APIs with a verified migration guide.
- Existing Catalog, Task, Result, Experience, presentation manifest/pattern/state mapping, runtime Region/action/data boundaries, and MCP/WebMCP/BYOK adapters remain the foundation.
- No new public package, hosted inference, account system, database, or public agent relay.
- Performance qualification remains deferred. Functional bounds, cancellation, cleanup, and browser dependency boundaries remain release requirements.
- Root is the sole implementation and integration owner under workspace instructions.

## Decisions and discoveries

- High-level APIs live in existing package subpaths: `core`, `runtime/app`, `web/app`, `web/recipes`, `react/app`, and `agent/app`.
- Zod is the initial runtime-schema path because it is already a core/runtime dependency. Existing Catalog input remains supported.
- Standard intent set: browse, detail, create, edit, compare, analyze. Search is a browse capability; navigation remains host-owned; workflows compose registered forms and actions.
- Agent input never contains authority, credentials, executable code, HTML, SQL, or module URLs. Agent proposals and manual intents share the same runtime entry.
- Public playground offers deterministic guided/manual modes. Real MCP/BYOK runs through the same playground from a local trusted host. Native WebMCP remains experimental and capability-detected.
- The public site remains one static artifact served on multiple hosts; route behavior distinguishes landing and docs surfaces.
- Registry inspection found npm tombstones for `@aeliqo/core@0.2.0` and `@aeliqo/react@0.2.0`: each package has a `time["0.2.0"]` record but no published version payload. npm will not permit those versions to be reused. The owner selected `0.3.0`; all six public packages, active applications, examples, runtime version constants, documentation, and release metadata moved together. A fresh read-only npm preflight confirms that all six `0.3.0` identities are available.

## Execution evidence

- Resource and intent kernel: `defineResource`/`validateResource`, generated or existing Catalog support, Zod record validation, six standard intents, namespaced custom intent registry, and deterministic `compileIntent` are exported from `@aeliqo/core`.
- Browse search is part of the QuerySpec contract and lowers to a reviewed `core.text.includes-casefold@1` function in the bounded planner/evaluator. It does not execute arbitrary expressions supplied by the caller.
- Missing and nullable values are not conflated: unsupported optional row fields fail with an actionable diagnostic and require a stable projection/default or explicit nullable value.
- Generated JSON schemas now include `intent.schema.json`; dependent Task/proposal schemas were regenerated from the same contract source.
- Evidence: `pnpm test:contracts` passed on the working revision with 16 test files and 181 tests, including TypeScript and independent JSON Schema parity.
- The runtime/app facade now owns mounting, fresh authority reads, intent compilation, evaluation, latest-request cancellation, Result/Region lifecycle, context discovery and presentation commit without importing DOM code. Authority/principal changes revoke stale materializations.
- The web/app facade uses the same runtime, standard recipes and registered Web Components. Browse adapts table-to-cards from container size without a model call; compare preserves a table on narrow containers; custom views remain trusted consumer code.
- Analyze intent selection now gives a registered temporal trend recipe higher semantic fitness than a generic tabular fallback. Exact values remain available and the policy still refuses an invalid or unregistered view.
- Create/edit compile to queryless form Tasks. Standard form nodes and bindings are derived from registered resource fields and existing input primitives. Create can start empty; edit refuses to invent state and requires a trusted `formState` adapter with current values and entity revision.
- User drafts remain host-owned, are transferred through the validated interaction state, and are merged into the registered action only at submission. The facade emits a preview callback; confirmation and execution remain explicit trusted-host operations. A single preview can now be cancelled without revoking unrelated action state.
- Nested form/repeater/multiselect payloads use bounded JSON through the interaction and action boundary; the obsolete scalar-only form check was removed.
- The agent/app facade exposes exactly `aeliqo_context`, `aeliqo_render`, and `aeliqo_act`. It sanitizes discovery/results, pins one session/Region, keeps confirmation outside agent tools, and reports `renderer-ready` only when using a real web render port. Trusted multi-resource discovery is explicit: the runtime lists only resources authorized for the same principal and scope, while a single-resource host remains the safe default.
- The local runner serves the same built playground on loopback, pairs one expiring browser Region, and keeps BYOK credentials in the Node process. Same-origin SSE calls require browser acknowledgments; MCP HTTP and stdio reuse the same bridge; expiry, cancellation, pending/byte limits, invalid origins, and invalid bearer credentials fail closed.
- Local-runner evidence: 5 broker lifecycle tests and 2 browser/transport tests pass. A real official MCP HTTP client and a spawned stdio client each discover exactly the three standard tools; MCP render changes the live Products Region and returns `renderer-ready`. Already-cancelled bridge calls fail immediately, event-stream write failures clean pending state, cross-site-style session navigation is rejected, and oversized MCP bodies stop at the Node ingress bound.
- Configured BYOK acceptance used DeepSeek `deepseek-chat` through the provider-agnostic OpenAI-compatible model port at the allow-listed `https://api.deepseek.com` origin. The runner limits requests to 128 kB each way, 30 seconds per provider call, one attempt, four turns/model requests/tool calls, and 36,000 total estimated tokens. The temporary key remained in the local process and was never written to the repository or evidence.
