# Candidate structural contracts — 0.1

This directory is a **reference subset to reconcile with the local PoC**, not an installed runtime or a new public industry standard. `types.schema.json` is the single reference source; the seven entry schemas reuse it. A production implementation chooses one authoritative schema authoring system and generates types, validators, tool subsets and docs from it. Do not add competing copies of these definitions elsewhere.

Schemas use draft 2020-12 and local URN references, never runtime network resolution. The indexed positive and negative fixtures document the intended candidate boundaries, but this reconciled repository does not ship the original kit validator; they are therefore specifications rather than executed runtime evidence. Component props are JSON-compatible configuration; the running registry validates its supported subset independently. Loader IDs and task/metric IDs are resolved against a trusted registry. A string of HTML or JavaScript never becomes executable merely because it is syntactically a string.

## Deliberately narrower than the architectural grammar

Included: dataset/metric descriptors, typed query predicates, component manifests, nodes/layouts/links, explicit operation batches, structured intents, and separate operation/render/data receipts. Not included: production auth transport, full DataPort implementation, schema-to-TypeScript compiler, arbitrary joins, advanced aggregations, custom transform execution, business actions, all-query selection tokens, collaboration, or real renderer acknowledgements. Current `selection.set` is explicit bounded keys; all-query selection needs a future server-issued scope contract, not an unbounded ID array.

Structural validation cannot prove referenced IDs exist, field uniqueness, key/grain correctness, dimension/unit compatibility, exact arithmetic, join cardinality, predicate type validity, layout tree ownership, port compatibility, acyclic routing, revision equality, authorization, URL safety in rendered content, or whether anything appeared on screen. Those need semantic validation and integration tests. Even two structurally valid receipts with mismatched render/workspace revisions must fail completion semantically.

Resource controls at runtime: maximum serialized request bytes; traversal depth (initial candidate 16 for predicates and 8 for layouts); request/node/port/row limits; bounded concurrent operations. Schema recursion alone is not a resource budget. Bound registry tools and never send full private datasets to an agent by default. The `per.quantity` monetary denominator must be strictly positive semantically, and currency codes must be validated against the app's actual supported set; a regex is not a full currency registry.

## Example safety and meaning

All fixture data and prices are synthetic. `synthetic:model-offers` is not a current model/pricing dataset. `metrics` in an intent can refer to compatible numeric fields or declared metric IDs; registry resolution decides, never field-name inference. `configure.props` means a validated shallow configuration merge with explicit replacement of values; it is not arbitrary JSON Patch and cannot change ownership, bindings or security context. Structural mutations must include an explicit valid layout update where required; no implicit reparenting is assumed. Removing a linked node requires explicit link removal and a valid resulting layout in the same batch.

A `completed` receipt in this candidate subset represents a workspace-output request, hence requires committed + acknowledged + ready/not-required. Partial results remain `pending` or explicitly explained failure in this subset. Future contracts may represent an accepted partial outcome only through a named policy and compatible version evolution. Human visibility itself is not proved by browser acknowledgement.
